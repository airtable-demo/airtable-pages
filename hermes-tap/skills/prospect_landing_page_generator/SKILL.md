# Prospect Landing Page Generator

Generates a personalized prospect landing page for Airtable AE outreach. Researches the account's brand colors, selects the two best-fit demo videos and two best-fit customer stories from the Airtable assets library, and publishes a HyperAgent webpage artifact.

## When to use

Use this skill whenever an Airtable AE asks to create a personalized landing page for a prospect — e.g. "build a landing page for [prospect] at [account]", "create a prospect page", "make a page for our meeting with X". Triggers also include explicit mentions of "POV page", "prospect site", or "personalized page".

## Required inputs (collect every time, refuse to proceed if any are missing)

1. **Prospect POV OR Prospect Title** — one of:
   - **Prospect POV** (preferred when the AE has done research): multi-line text describing the prospect's role, observed signals, why this person matters, what's specifically interesting about their team / function / scope.
   - **Prospect Title** alone (acceptable shortcut): if the AE only gives a job title like "Director Product Development & Commercialization", you (the agent) SYNTHESIZE the Prospect POV in Phase 0 by combining the title with the Account POV + general Airtable narrative. The synthesized POV should be 2-3 sentences, name what the role implies, connect to the account's situation, and reference an analogous customer outcome. Treat the synthesized POV as the canonical Prospect POV for downstream phases.
2. **Prospect Name** — full name.
3. **Account Name** — the company name as they brand themselves.
4. **Account POV** — multi-line text. The account's overall situation, expansion plans, observed signals, why the timing is now, what an Airtable rollout would unlock.
5. **Calendar Link** — full URL (e.g. `https://calendar.app.google/...`). Every CTA button on the page links here.

Optional inputs:
- Prospect Title (when not given as the POV source — used in the hero chip for clarity)
- Account Domain override — if the agent can't derive the right domain from Account Name (defaults to `accountname.com` lowercased)
- Prospect Logo URL override — if Google favicons doesn't return a usable logo for the account, the AE can pass a direct image URL or pre-uploaded asset URL
- **Prospect Profile Pic URL** — direct image URL (e.g. a `media.licdn.com/dms/image/...` URL copied from LinkedIn). When provided, renders the prospect's photo above the H1 alongside the AE's photo (if available). Skip the entire `.hero-photos` block if no pic is resolved.
- **Prospect LinkedIn URL** — e.g. `https://www.linkedin.com/in/<slug>`. Used as a fallback signal for `SearchImages`-based profile pic discovery when no direct image URL is provided (Phase 1.5 below).

**AE identity (per-AE state, persisted to agent memory for this cloned instance)**:
- **AE Name** — appears in the "Prepared for {prospect} by {ae_name}" nav line and the "Prepared by {ae_name} · Airtable" footer note.
- This is the running AE's name — NEVER hardcode it. Each AE who clones this skill / agent gets their own value persisted to THEIR cloned agent's memory.

## Phase 0 — Intake

### Phase 0a — AE identity capture (FIRST-RUN-ONLY)

Before collecting prospect/account inputs, the agent MUST know the running AE's name. Each cloned agent instance has its own isolated memory store, so when a new AE clones this skill into their own agent, the memory starts empty and Phase 0a runs.

1. Call `SearchKnowledge({ query: "AE name landing page prepared by", types: ["memories"], limit: 3 })` to look up the saved AE name.
2. If a memory exists with content matching `My AE name for the "Prepared by ..." line on landing pages is <NAME>.`, extract `<NAME>` and use it for the rest of the run. Done.
3. If no such memory exists, ask the user EXACTLY ONCE before Phase 0b:
   > Before we start: what's your name for the "Prepared by ..." line on your landing pages? (e.g. "Jane Smith" — appears once in the nav and once in the footer)
4. When the user answers with a name, call `CreateMemory` with:
   - `content`: `My AE name for the "Prepared by ..." line on landing pages is <NAME>.`
   - `category`: `user_fact`
   - `importance`: `5`
   - `whenToUse`: `Use this AE name in the "Prepared for ... by <NAME>" nav line and "Prepared by <NAME> · Airtable" footer of every landing page generated by the prospect_landing_page_generator skill.`
   - Include the returned `[[MEMORYCONFIG_xxx]]` placeholder in your reply.
5. **Also capture the AE's own profile photo (optional, one-time)**: in the same first-run flow, ask:
   > Optional: paste your LinkedIn profile photo URL if you want your headshot to appear in the hero of every landing page. Right-click your photo on LinkedIn → "Copy image address" → paste. Tip: these URLs expire after 30-90 days; refresh by repeating the steps when needed. Skip if you'd rather render pages without it.
   - If the AE provides a URL: call `CreateMemory` with `content`: `My AE LinkedIn profile photo URL for landing pages is <URL>.`, `category`: `user_fact`, `importance`: `4`, `whenToUse`: `Use this AE profile photo URL above the H1 of every landing page generated by the prospect_landing_page_generator skill, alongside the prospect photo (if any).`
   - If the AE skips: do not write any memory. Subsequent runs simply omit the AE photo from the hero (only show the prospect's photo if provided, or skip the whole .hero-photos block).
6. Proceed to Phase 0b only after Step 4 completes (name captured; AE photo is optional).

### Phase 0b — Per-prospect intake (runs every time)

Ask the AE to provide all five required inputs in a single message. If anything is missing, list ONLY the missing items and ask for them. Do not proceed until all five are present.

If the AE provided a Title instead of a Prospect POV (input #1 shortcut), synthesize the POV before moving on:
- Combine the title with the Account POV
- 2-3 sentences referencing what the role implies for this account at this scale
- Anchor to an analogous customer outcome (e.g. "Given how Raising Cane's standardized their opening playbook in Airtable to cut weeks from each launch, we think there's a clear path to turn your opening pipeline into a repeatable, visible system that scales with your growth.")
- Confirm the synthesized POV back to the AE in the echo step so they can quickly correct if it's off

When the AE confirms all inputs, echo them back compactly so they can double-check before generation. Example (placeholders in angle brackets — substitute the real values from inputs and memory):

> Generating with:
> Prospect: <Full Name> (<Title>)
> Account: <Account> (<account_domain>)
> Calendar: <calendar_link>
> Prepared by: <ae_name pulled from memory — never hardcoded>
> POV: <synthesized POV if generated from a title, else "received as-is">
> Researching brand colors and selecting assets now.

## Phase 1 — Brand Color Research

Goal: pick a primary brand color (`--accent`), a background color (`--bg`), and a decision on light vs dark theme. The colors must come from real research, not invention.

1. Derive the account domain from the account name. Default: lowercase the company name, strip non-letters, append `.com` (Chipotle → chipotle.com). If the AE provided a domain override, use that.
2. Use `ExaSearch` with query `"<Account Name> brand color"` or `"<Account Name> official website"` to find the primary site URL and any branding references.
3. Use `WebFetch` (or Browser tools as fallback) on the official website to read its `<head>`. Look for, in order:
   - `<meta name="theme-color" content="#...">` — strongest signal
   - The `<link rel="icon">` favicon URL (visual sanity check)
   - Background or accent colors mentioned in inline CSS / linked stylesheets
4. If the AE has provided a logo URL or mentioned a specific color in the POV ("Chipotle red", "Blackrock yellow"), use that as the authoritative source instead.
5. Pick light or dark theme based on the brand identity:
   - Brands with bold dark or saturated palettes (Chipotle red, Coca-Cola red, Nike black, Tesla black) → **dark theme** (background near-black with brand tint)
   - Brands with light, airy, minimal palettes (Apple, Notion, Stripe) → **light theme** (background near-white)
   - When in doubt → dark theme (matches the Cloudflare reference set)
6. Fallback if all research fails: `--bg: #0F0F14` (very dark blue-black), `--accent: #2563EB` (a neutral assertive blue), dark theme.

Output of Phase 1 (hold these as variables for Phase 3):

```
account_domain = "chipotle.com"
theme = "dark"
brand_color = "#A81612"
bg_color = "#0D020C"
brand_hover = "rgba(168,22,18,0.82)"  # 82% alpha of brand
brand_glow = "rgba(168,22,18,0.42)"   # 42% alpha
brand_muted = "rgba(168,22,18,0.10)"  # 10% alpha
brand_ring = "rgba(168,22,18,0.28)"   # 28% alpha
text_primary = "#F0F0F8"              # near-white for dark theme, "#1F1F33" for light
text_secondary = "rgba(240,240,248,0.50)"
text_tertiary = "rgba(240,240,248,0.48)"
```

Derive all alpha-suffixed variables from the brand color RGB at the canonical alpha levels (6%, 4%, 50%, 48%, 38%, 28%, 22%, 18%, 12%, 10%, 8%, 7%, 6%, 5%, 4%, 2%). See `canonical_template.html` `:root` block for the proportions.

## Phase 1.5 — Profile Pic Resolution

Goal: resolve up to two hero photos (Prospect + AE) into base64-inlined data URIs for the `.hero-photos` block above the H1. Render the block only when at least one pic resolves.

### Step A — Resolve the prospect's photo (tiered)

**Tier 1 — Direct image URL provided** (best path):
- If the AE passed a `Prospect Profile Pic URL` (a direct `https://...` image URL — typically `media.licdn.com/dms/image/...`):
  - `curl -sL "<URL>" -o /tmp/prospect_photo.jpg` → check `Content-Type: image/*` in response headers (use `-I` first to validate)
  - Base64-encode: `base64 -w 0 /tmp/prospect_photo.jpg`
  - Set `prospect_photo_data_uri = "data:image/jpeg;base64,..."`
  - Note: LinkedIn URLs include `?e=<timestamp>`. If the timestamp is in the past, the URL returns 403 `deny-expired-url` — surface that to the AE and ask them to re-copy from LinkedIn.

**Tier 2 — LinkedIn URL provided, no direct image URL** (auto-discovery):
- If the AE passed only a `Prospect LinkedIn URL` (e.g. `https://www.linkedin.com/in/<slug>`):
  - Run `SearchImages({ query: "<Prospect Name> <Account Name> LinkedIn", numResults: 5 })`
  - For each result, check whether `sourceUrl` matches or shares the slug from the LinkedIn URL the AE provided (substring match on the `/in/<slug>` path).
  - If a result matches, use its `imageUrl`. Curl + base64 it as in Tier 1.
  - **Verification**: surface the matched image inline in the echo step ("Found this LinkedIn photo for Dave Snyder — confirm or paste a different URL"). Only proceed if the AE confirms.
  - If no result matches the LinkedIn slug confidently, fall back to Tier 3.
  - Note: results with `e=2147483647` in the URL (year 2038) effectively never expire — Google's cached versions are stable. Results with shorter `e=` timestamps are the LinkedIn-fresh ones that expire.

**Tier 3 — Skip**:
- No prospect pic available. Render the hero WITHOUT a prospect photo. If the AE photo is available, show only the AE photo (rare). Otherwise skip the entire `.hero-photos` block.

### Step B — Resolve the AE's photo (memory-driven)

- Read the memory written in Phase 0a step 5 (`SearchKnowledge` with query `"AE LinkedIn profile photo URL landing page"`).
- If found, curl + base64-inline the URL → `ae_photo_data_uri`.
- If the URL has expired (403 `deny-expired-url`), tell the AE: "Your LinkedIn photo URL has expired. Want to refresh it now?" — if yes, capture and overwrite the memory; if no, proceed without.
- If no memory exists, proceed without the AE photo.

### Step C — Decide the hero-photos block layout

- Both photos resolved → render `<prospect_photo> × <ae_photo>` (mirrors the original Cloudflare example design)
- Prospect only → render `<prospect_photo>` (single photo, centered)
- AE only → render `<ae_photo>` (single photo, centered) — uncommon path, but supported
- Neither → omit the `.hero-photos` block entirely; H1 floats up as if the block wasn't there

## Phase 2 — Asset Selection

Goal: pick 2 demo videos and 2 customer stories from the Assets table at base `appiwo5qAXaewDXHu`, table `tblWkh1kC4aifkBj0`.

1. Call `ExecuteIntegration` with action `AIRTABLE_LIST_RECORDS`, base_id `appiwo5qAXaewDXHu`, tableIdOrName `tblWkh1kC4aifkBj0`, maxRecords as needed (cap 100 — fetch all). Use `paramsFile` if the response payload is large.
2. Partition records by `Type`:
   - `Video` → videos pool
   - `Customer story` → stories pool
   - blank/other → ignore
3. **Derive the POV's primary function FIRST** (`pov_function`) — exactly one bucket from the function_lob taxonomy (Product & Design / Marketing & Communications / Sales & Account Management / Software Development / Operations / Finance / HR / IT & Support / Customer Service / Legal). If the caller passed a function (e.g. an account play's Databricks `function_lob` / `adjacent_function_suggestion`), use it; otherwise classify from the prospect POV + account POV + title. The demo video is the highest-risk pick: a demo from the wrong function (a marketing-campaign demo on a product POV) is the exact failure this gate prevents.
4. Apply `asset_selection_prompt.md` with `pov_function`. It enforces a HARD function gate on demo videos (a cross-function demo is INELIGIBLE unless zero same-function demos exist, then explicitly flagged) and a strong function preference on stories, then ranks the function-eligible assets by industry / persona / use case / scale / measurable outcome. Write the selection JSON (with `target_function`, per-asset `asset_function` + `function_match`, and the `function_check` self-audit) to `/agent/workspace/asset_selection.json`:

```json
{
  "target_function": "Product & Design",
  "videos":  [ { "record_id","name","url","description","asset_function","function_match","rationale" }, { "...": "..." } ],
  "stories": [ { "record_id","name","description","asset_function","function_match","rationale" }, { "...": "..." } ],
  "function_check": "..."
}
```

5. **Validate the selection (mandatory) — never ship an unvalidated pick:**
   ```bash
   python3 "/agent/workspace/skills/prospect_landing_page_generator/validate_asset_selection.py" \
     --file /agent/workspace/asset_selection.json --strict --json
   ```
   The validator deterministically re-derives each asset's function from its own text and FAILS (exit 2) on a cross-function demo regardless of what the ranker self-reported. On a non-zero exit, RE-PICK the offending asset with a same-function alternative and re-validate until it passes (exit 0/1). A flagged fallback is justified ONLY by a genuinely empty in-function pool — call it out in the AE-facing summary.

Note: not all rows have URL, Industries, Personas, or Use cases populated. Judge an asset by whatever fields are present, but the function gate (step 4-5) always applies.

## Phase 3 — HTML Generation (script-based for speed)

**This phase is now executed by a Python build script, not by the LLM.** Inline HTML/CSS regeneration was the biggest bottleneck — the script reduces Phase 3 from ~60-90 seconds of LLM reasoning to under 1 second of pure string substitution + media fetching.

### Inputs the LLM gathers BEFORE calling the script

The agent prepares a JSON input file with these keys. Most come straight from Phase 0-2; a small subset are generated by the LLM (Sonnet sub-agent recommended for the content fields):

```
{
  "theme": "light" | "dark",
  "brand_color": "#<6-char hex from Phase 1>",
  "ae_name": "<from Phase 0a memory>",
  "ae_photo_url": "<from Phase 0a memory or null>",
  "prospect_name": "<Prospect Full Name>",
  "prospect_first_name": "<Prospect First Name>",
  "prospect_title": "<Prospect Title>",
  "prospect_photo_url": "<Phase 1.5 resolved URL or null>",
  "account_name": "<Account Display Name>",
  "account_domain": "<accountdomain.com>",
  "calendar_link": "<per-run input>",
  "headline": "<6-10 words derived from POVs>",       // LLM-generated
  "hero_subhead": "<2-3 sentences>",                  // LLM-generated
  "value_headline": "<specific to account>",          // LLM-generated
  "value_cards": [                                     // LLM-generated (4 items)
    {"icon": "connect|grid|globe|spreadsheet|star|shield|chart", "title": "...", "body": "..."},
    ...
  ],
  "diagram_label": "<process name>",                  // LLM-generated
  "diagram_nodes": ["Step 1", "Step 2", "..."],       // LLM-generated (3-6 nodes)
  "videos": [                                          // From Phase 2
    {"media_id": "<wistia hashed id>", "label": "<readable title>"},
    {"media_id": "<wistia hashed id>", "label": "<readable title>"}
  ],
  "stories": [                                         // From Phase 2 + LLM-rendered modal copy
    {
      "title": "<asset name>",
      "csr": ["Challenge: ...", "Solution: ...", "Result: ..."],
      "modal_headline": "<asset name>",
      "modal_sections": [
        {"label": "Challenge|Solution|Result|Themes|Why it matters for <account>", "body": "..."}
      ]
    },
    ...
  ],
  "proof_quote": "<optional pull quote>"
}
```

### Call the script

```bash
python3 /agent/workspace/skills/prospect_landing_page_generator/build_landing_page.py /tmp/input.json /agent/workspace/landing_page.html
```

The script:
- Loads `canonical_template.html`
- Computes the full theme palette (CSS variable values) from `theme` + `brand_color` — alpha variants, gradients, modal backgrounds, etc.
- Fetches the account favicon via Google favicons → base64-inlines
- Fetches Wistia bundle JSON for each video → extracts the 540p mp4 URL + thumbnail URL → downloads + base64-inlines the thumbnail (mp4 stays as a remote URL, browser streams it)
- Fetches profile photos if URLs provided → base64-inlines (auto-resizes via Pillow)
- Renders sub-components: hero-photos block (conditional), value cards, workflow diagram SVG, video elements, story cards + modals
- Substitutes everything into the template via mustache-style `{{KEY}}` markers
- Writes the final HTML

### What the LLM still does (content only, not layout)

- Synthesizes the Prospect POV if only a title was given (Phase 0b)
- Generates the headline, hero subhead, value-card titles+bodies, value-headline, diagram-label, diagram-nodes
- Picks the top 2 demo videos and 2 customer stories from the assets base (Phase 2)
- Writes the modal Challenge/Solution/Result/Themes/"Why it matters for X" copy for each story
- Picks an `icon` keyword for each value card from the supported set

These are all CONTENT decisions where Opus-level judgment matters. Everything else — CSS, HTML structure, base64 inlining, asset URL extraction, theme palette computation, responsive breakpoints — is deterministic and handled by the script.

### Speed budget (target per run, post-optimization)

| Phase | Before | After |
|---|---|---|
| Phase 0 intake | ~5s | ~5s (no change — conversational) |
| Phase 1 brand colors (parallelized) | ~10s | ~3-5s (ExaSearch + ExaContents in parallel) |
| Phase 1.5 profile pics | ~5s | ~2s (curl + base64 directly) |
| Phase 2 asset selection | ~15s | ~5-8s (Sonnet sub-agent, not inline Opus) |

### Parallelization

Phase 1, Phase 1.5, and Phase 2 have no dependencies on each other. The agent should dispatch them concurrently (multiple Agent or tool calls in the same message) when the prospect/account inputs land, instead of serializing.

### Sonnet for asset ranking

Don't use inline Opus reasoning to rank all 67 assets. Instead:

1. Pre-filter to ~10-15 candidates by keyword match (use case mentions, industry terms) against the POVs in Python or inline.
2. Dispatch a Sonnet sub-agent (`subagent_type: "default"`, `model: "sonnet"`) with the candidate list and POVs. Sub-agent returns the chosen 2 videos + 2 stories as JSON.
3. Sub-agent has a tight prompt: "Pick the 2 best videos and 2 best customer stories for this prospect, given these candidates. Return JSON: {videos: [{media_id, label}], stories: [{title, asset_id}]}."

## Phase 4 — Publish

1. Call `PublishWebpage` with:
   - `filePath: "/agent/workspace/landing_page.html"`
   - `title: "<Prospect First Name>'s Airtable × <Account Name> preview"`
2. Capture the returned `[[ARTIFACT_xxx]]` placeholder.
3. Reply to the AE with:
   - Compact summary line: "Landing page ready for <Prospect Name> at <Account Name>. Theme: <dark|light>. Brand color: <hex>. Videos: <2 names>. Stories: <2 names>."
   - The `[[ARTIFACT_xxx]]` placeholder on its own line so the preview renders inline.
   - One follow-up offer: "want to tweak any section, swap an asset, or generate another?"
4. Do NOT save the HTML, the calendar link, or any prospect data to memory after a run. Each run is isolated.

## Quality bar

- The hero headline must reference a SPECIFIC observation from the POVs — never generic.
- Brand colors come from real research; never invent.
- Videos and stories come ONLY from the Airtable assets base. Never invent assets or use external URLs.
- Calendar link is per-prospect input. Never hardcode.
- Image / iframe guardrails followed (Google favicons URL or base64-inline; no crossorigin attribute; clickable poster cards for videos).
- No hero profile photos (removed after iteration).
- Output is a single self-contained HTML file. The only external loads are Google Fonts. Logo and video posters are base64-inlined; calendar / video / story-modal links use `target="_blank"`.

## Error handling

- Airtable query fails → ask the AE to re-confirm the assets base is accessible; do not fall back to invented assets.
- Brand color research fails completely → use the fallback palette and tell the AE: "couldn't pull brand colors automatically; used a neutral dark palette — let me know if you want to swap to a specific color."
- Fewer than 2 videos or 2 stories matched well → use the closest matches and tell the AE which ones felt thin.
- PublishWebpage fails → retry once; if still failing, save to a local file and surface the path.

## Portability checklist (must pass before this skill is considered shareable)

For this skill to work for ANY AE who clones the agent, the following invariants must always hold:

1. **No AE-specific data baked into the skill** — no hardcoded names, emails, calendar links, SFDC IDs, Outreach IDs, or company-specific values. Everything user-specific comes from one of:
   - Per-run inputs (prospect name, account, POVs, calendar link)
   - Per-AE memory written via `CreateMemory` (currently only `ae_name`; could later include preferred calendar default, preferred theme, etc.)
2. **AE name lookup uses `SearchKnowledge`, not hardcoded values** — Phase 0a `SearchKnowledge({ query: "AE name landing page prepared by" })` is the authoritative read. If the read returns nothing, the agent must ask the user and write a new memory.
3. **Memory write uses `CreateMemory`** — the agent NEVER assumes the AE has any memories pre-populated. First run of the skill in a fresh cloned agent ALWAYS triggers Phase 0a.
4. **Skill scripts (`canonical_template.html`, `generation_prompt.md`, `airtable_logos.md`, `asset_selection_prompt.md`) contain `{{AE_NAME}}` / `${ae_name}` placeholders** — not real names. The agent fills them at runtime from the captured value.
5. **The Airtable assets base (`appiwo5qAXaewDXHu`) is shared** — it's the canonical Airtable-internal asset library that every AE reads from. It is NOT per-AE state; do not promote it to user input.
6. **Calendar link is per-run input** — it is intentionally NOT saved to memory. Different prospects may need different calendar links (e.g. an AE running both a personal Google Calendar and a Calendly link for a co-AE meeting).
7. **Prospect Profile Pic URL / LinkedIn URL are per-run inputs** — never saved to memory (prospect-specific). AE's own LinkedIn photo URL IS in memory (Phase 0a step 5) since it's reused across every page that AE generates.
8. **No leaked example identifiers in docs** — when the skill documentation shows examples, it uses angle-bracket placeholders (`<NAME>`, `<account>`, `<calendar_link>`), not real names or IDs.

If a future change to the skill would violate any of these (e.g. an "Account Domain default" that bakes in a specific company), tag it as breaking portability and surface the trade-off in the agent's response.
